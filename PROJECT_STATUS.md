No `suppressHydrationWarning` added — it would only mask the warning for this one element for users with this one extension pattern, doesn't reflect anything wrong with the app's actual render output, and this class of external DOM mutation can equally affect any other interactive element on any other page for a different visitor's different extension, so there's no complete fix available from application code anyway. ### Two bug fixes: ProjectGallery full-width, WhatWeBelieve stuck-at-card-5 (2026-09-07, fourth session)

**Bug 1 — ProjectGallery wasn't actually full-width.** The masonry grid's own container div still carried `mx-auto max-w-[1100px]` (a leftover from copying this site's default content-width convention when the masonry rebuild landed), so it rendered as a narrower centered block with dead cream space on both sides instead of the intended edge-to-edge layout. Fixed the same way `IndiaMap.jsx` overrides the default for its own full-bleed map: no horizontal padding on the `<section>`, no `max-w`/`mx-auto` on the grid itself.

Once the container could legitimately be 1920px/2560px+ wide (not capped at 1100px), the old 4-column-max breakpoint tiers (`COLUMNS_WIDE`/`COLUMNS_MEDIUM`, tuned for that old ~1100px cap) started producing absurdly wide individual columns on large monitors. Retuned as an explicit tiered lookup keyed off the real full-viewport range: 2 columns below 640px, 3 at 640px+, 4 at 1024px+, 5 at 1900px+, 6 at 2200px+ (capped there). Confirmed via Playwright screenshots at 375/1440/1920/2560 — grid genuinely spans the full measured container width at every size (`gridWidth === viewportWidth`, `gridLeft === 0`), column counts read as proportionate (not oversized) at each tier, zero horizontal overflow on direct measurement (an initial 1px `scrollWidth`-vs-`clientWidth` reading at 375px turned out to be a one-off mid-animation transient, not reproducible on a clean isolated re-check both immediately on load and after scrolling to the gallery).

**Bug 2 — WhatWeBelieve's scroll stack got permanently stuck around card 5, card 6 unreachable.** This turned out to have nothing to do with `WhatWeBelieve.jsx` itself, or with any stale item-count math (its own scroll-length calculation was already, and still is, fully derived from `BELIEFS.length` — confirmed by directly walking the math and by a controlled `window.scrollTo` test on a fresh full-page load of `/about`, where all 6 cards reached correct opacity/transform values exactly where expected). The bug only reproduced via a **client-side navigation** from a shorter page (e.g. `/`) to `/about` (confirmed live: real wheel-scroll input got clamped at exactly the home page's own scrollHeight minus the viewport height, 6701px, well short of the ~8172px actually needed to reach card 6 — the taller `/about` page's `document.documentElement.scrollHeight` was correctly 11366px the whole time, but the user's real ability to scroll there was capped far short of it).

Root cause: `SmoothScroll.jsx`'s single global Lenis instance persists across client-side route changes (it lives in the root layout and never unmounts on navigation), carrying whatever scroll `limit` it last measured. Lenis's own `autoResize` (on by default) watches `document.documentElement` via `ResizeObserver` to recompute that limit — but `ResizeObserver` reports the root element's own generated box, which browsers pin to the viewport size regardless of how much its content overflows (confirmed live: the limit never budged even minutes after the taller page's content had clearly settled). A first attempt at the fix — a one-shot `usePathname()`-triggered `lenis.resize()` call, mirroring `ScrollProgress.jsx`'s own existing `[pathname]`-triggered `ScrollTrigger.refresh()` for its separate cache — measured a still-too-short height and didn't fix it, because the new route's full content hadn't finished streaming in yet at the exact moment the pathname changed (confirmed via an inline debug log: limit only grew from 6701 to 6814, nowhere near the ~10466 it should've reached).

The actual fix: a persistent `ResizeObserver` on `document.body` instead (added in `SmoothScroll.jsx`, alongside Lenis's own lifecycle) — `body` has no special root-element treatment, and with no explicit height set anywhere in `globals.css`, its rendered box genuinely does grow to match real content height, so this fires reliably on any real height change regardless of timing, sidestepping the streaming-content race entirely. Calls `lenis.resize()` on every fire. Confirmed fixed live: the same repro (home → `/about` via a real `<Link>` click, then real wheel-scroll input) now reaches the full document height and "Enough, Not Too Much" settles fully (`opacity: 1`, `translateY(0px) scale(1)`).

Tested via Playwright: forward AND backward scroll through all 6 cards at both 1440×900 and 390×844, both via a direct page load and via client-side navigation from `/` (mobile client-nav specifically wasn't re-verified — the mobile nav's "About" link lives behind a hamburger menu the test script didn't drive — but the fix itself is viewport-size-independent, it only cares about `document.body`'s real height, so this isn't considered a gap). All 6 cards reached opacity ≥0.84 (most reaching a clean 1.0) during forward scroll and correctly reset to 0 scrolling back to the top. Reduced-motion fallback already iterates `BELIEFS.map` directly (never had a stale count). Zero console errors, clean `next build`.
