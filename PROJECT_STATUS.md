### Projects listing cards: hover-reveal name + location over a frosted blur strip (2026-09-08, twenty-first session)
Client reference: cards should show only the photo by default, with the project name and location fading in over a blurred/frosted scrim at the bottom of the photo on hover. - **Default state:** clean photo, no scrim, no text — the old always-on `bg-gradient-to-t from-black/50` and name `<p>` are both gone.
- **Overlay:** a single absolutely-positioned bottom strip, sized to its content (icon + name + location + padding) rather than a fixed fraction of the card, so it reads as a "strip" rather than covering half the photo. Background is an ink-toned gradient (`rgba(43,38,34,...)`, i.e. `#2B2622` at varying opacity, fading to fully transparent above) plus a real `backdrop-filter: blur(14px)` (with the `-webkit-` prefix set explicitly, not relying on a Tailwind utility, for guaranteed Safari support) for the frosted-glass look — ink-toned per the brand-token rule, not black. Content: a small circular "view project" icon (a plain diagonal-arrow line SVG, following the exact convention `ProjectGallery`'s/`ProjectDescriptionModal`'s existing close icons already use — `strokeWidth="1.5"`, round caps/joins, `currentColor` — since this codebase has no icon library and this reuses that pattern rather than adding one), then the project name, then its location (`project.location`, already real data from `src/data/projects.js` via `getAllProjects()` — no new/invented location strings). Text color switched from the old plain `text-white` to brand-token `CREAM`, matching every other light-on-dark text treatment on this site.
- **Reveal mechanic:** plain CSS (`opacity`/`translate-y` + `transition`), no GSAP — this is a hover interaction, not a scroll animation, per the task's own guidance. `group-hover:`/`group-focus:` Tailwind variants on the card's existing `.group` class (the `Link` itself, already focusable) drive the reveal; `ease-out`, `duration-300`.
- **Touch fallback — always-visible at reduced opacity, chosen deliberately:** confirmed via `grep` that no hover/touch-detection precedent exists anywhere else in this codebase, so this follows the task's own suggested default for exactly that situation. A local `useState`+`useEffect`+`matchMedia("(hover: hover) and (pointer: fine)")` check (same idiom `About.jsx` already uses for its own `isDesktop` check, not a new shared hook for one caller) drives a `canHover` flag: hover-capable devices get the animated 0→1 reveal described above; devices that can't hover get the overlay permanently rendered at `opacity-90` instead of `opacity-100` — reasoning: several cards are visible at once while scrolling a mobile grid, so a full-strength scrim on every one of them simultaneously reads heavier than the same scrim appearing transiently under a cursor on desktop, so it's dialed back slightly rather than matched 1:1.
- **`prefers-reduced-motion`:** on hover-capable devices, `reduceMotion` (from the existing `useReducedMotion` hook) drops the `transition`/`translate-y` classes entirely so the reveal snaps instead of animating, while the underlying `group-hover`/`group-focus` opacity toggle keeps working — the reveal logic itself is untouched, only the motion is removed, per the task's own instruction.

- **`src/app/api/contact/route.js`** (new) -- a `POST` route handler that re-validates all 7 fields server-side against the same field list `ContactForm` submits (never trusts the browser's own `required` alone, since a direct POST bypasses it), checks the email against a simple regex, and -- once both pass -- sends the enquiry via `nodemailer` over SMTP. Sends both a plain-text and an HTML body; every field is passed through a local `escapeHtml()` before landing in the HTML body, since these are visitor-submitted strings going straight into an email client's renderer. Missing-field and invalid-email cases return `400` with a specific message; a missing SMTP config or a `sendMail` failure both log the real error via `console.error` server-side but return a clean, generic visitor-facing message (`500`/`502`) that never names which exact env var is absent -- that's internal deployment detail, not something a site visitor should see.
