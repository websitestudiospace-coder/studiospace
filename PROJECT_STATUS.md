## 3. Last diagnostic finding (context, not an open bug)

A "What We Believe section not showing" report was investigated this session and found to be a **false alarm** — caused by a Playwright `fullPage: true` screenshot capture that doesn't fire real scroll events, which froze *every* scroll-triggered reveal on the entire page (not just this section) mid-animation at their initial hidden `gsap.set()` state, in that one diagnostic capture only. Confirmed via real navigation + real scrolling (a fresh browser context, double page reload, `scrollIntoViewIfNeeded`, then reading live computed `opacity`/`transform`) that the section renders correctly, with zero console errors and a clean dev-server compile log. No code defect, no fix was needed.

**Flag for future sessions:** if a "section X isn't showing" report comes up again, check whether it's based on a full-page/no-scroll screenshot capture method before assuming a regression — that capture pattern will falsely appear to break *any* scroll-triggered section on this site, not just this one.

**Second, separate false alarm, same session:** a follow-up report claimed WhatWeBelieve's heading "never becomes visible." Worked through all 6 hypotheses offered (clip-vs-travel-distance, golden-rule violation, missing preloader gate, char-split timing, degenerate scrub range, missing refresh) with live measurement, not just reasoning — `ScrollTrigger` start/end, `.progress`, and each character's actual computed `opacity` were read directly from the page at every step. Found no reproduction: forward scroll, backward scroll, a genuine second pass through the trigger, both viewports, both a `scrollTo`-jump method and real mouse-wheel-driven Lenis scroll, a cold browser context with no cache — every single one revealed the heading correctly, 0→1 and back, zero console errors. (One early test run *did* appear to show it stuck at opacity 0 on a second pass — that turned out to be a bug in the diagnostic script's own scroll-position math, not the app; re-run with corrected math, it passed cleanly. Worth remembering before trusting a "reproduced it" result: check the test script's own arithmetic first.) No heading code was changed as a result.

**Third report, third investigation — this time DOM-level, not scroll-math.** Explicitly avoided re-testing scroll progress; instead queried the live DOM directly via Playwright `.evaluate()`, matching the exact repro scenario described ("bare cream space above the '01 Honest Materials' card"):
- `document.querySelectorAll` on the heading's char spans returns **13 elements** (correct — "What We Believe" has 13 non-space characters), each with correct `textContent` (`W`, `h`, `a`, `t`, `W`, `e`, `B`, `e`, `l`, `i`, `e`, `v`, `e`) and correct pre-scroll initial inline style (`opacity: 0`, `transform: translate(0%, 120%) scale(0.7, 2.3)`) confirmed via `outerHTML`.
- At the exact scroll position where "Honest Materials" is in view (`scrollY: 3585`, reached via `scrollIntoViewIfNeeded` on the card, matching the reported screenshot): all 13 chars read `opacity: "1"`, heading `getBoundingClientRect()` = `{top: 156.5, bottom: 252.5, left: 170, width: 1100, height: 96}` — fully inside the 900px-tall viewport, not clipped, not off-screen.
- Walked every ancestor from the `<h2>` to `<body>` (h2 → the `max-w-[1100px]` div → `<section>`): all three report `opacity: "1"`, `visibility: "visible"`, `display: "block"`; only the `<h2>` itself has `overflow: hidden` (intentional, matches its own content height of 96px, not clipping anything); no ancestor has `height: 0` or an unexpected second clip.
- First card's `getBoundingClientRect()` at the same scroll position: `top: 332.5` — 80px **below** the heading's `bottom` (252.5), confirming no paint-order/z-index overlap between them.
- Repeated with real `page.mouse.wheel()` scrolling (no programmatic `scrollTo` at all) — same result, chars readable mid-scrub in the correct reading-order sequence, no bug.
- Repeated against a full **production build** (`npm run build && npm run start`, served on a separate port, not the dev server) — identical result: 13 chars, correct text, all `opacity: "1"` at the repro scroll position.
- Two screenshots taken at the exact query moments (dev server and production) both show the heading fully legible ("What We Believe" in dark ink Agatho), matching the queried DOM state exactly — no discrepancy between computed style and actual paint.

**Conclusion: could not reproduce "renders nothing" at the DOM level either, across dev server, real wheel scroll, and a production build.** This is not another "verified working, nothing to see" — it's a genuine dead end from this environment's testing capability, and it's now worth treating as such rather than running a fourth identical investigation. What would actually move this forward: **the exact URL being viewed when this is observed** (confirm it's this repo's own `localhost:3000`/`next start`, not a separately-deployed Vercel preview that may be behind on commits — no `.vercel/` folder exists in this checkout, so a stale deployed preview is a real possibility that can't be checked from here), and if it truly is this same code, **the literal output of `document.querySelector('h2').outerHTML`** pasted from the browser session where it's blank — that single piece of evidence would show directly what differs between that render and everything reproduced here, rather than another round of guessing at a cause that all available testing says isn't in this file.
